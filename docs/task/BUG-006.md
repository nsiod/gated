# BUG-006 Fix Kubernetes upstream CA verification in gated proxy

- **status**: completed
- **priority**: P1
- **owner**: Codex
- **createdAt**: 2026-04-23 14:54

## Description

The Kubernetes proxy in `gated-protocol-kubernetes` can connect to
upstream clusters with token auth or mTLS client auth, but it has no way
to trust a self-signed or private Kubernetes API CA when
`tls.verify = true`. In that case upstream requests fail inside the
proxy with a reqwest TLS error like `invalid peer certificate:
UnknownIssuer`, even when the cluster presents the correct apiserver
certificate and the target URL matches the certificate SAN.

Acceptance criteria:

- Kubernetes targets can optionally carry an upstream CA PEM bundle.
- When `tls.verify = true`, the proxy uses the configured CA to verify
  the upstream Kubernetes API certificate chain.
- Existing `tls.verify = false` behavior remains unchanged.
- Integration coverage includes a Kubernetes target with
  `tls.verify = true` and a custom CA.

## ActiveForm

Implementing Kubernetes upstream CA handling for gated proxy requests.

## Notes

- Investigation traced all upstream Kubernetes API and websocket traffic
  through `create_authenticated_client()` in
  `crates/gated-protocol-kubernetes/src/server/auth.rs`.
- `TargetKubernetesOptions` currently exposes only `cluster_url`, `tls`,
  and `auth`; there is no field for an upstream CA bundle.
- Existing Kubernetes integration tests only cover
  `tls.verify = false`, so the self-signed CA verification path is
  untested.
- Implemented optional `ca_certificate` support on Kubernetes targets,
  wired the PEM bundle into reqwest root certificates, and exposed the
  field in the admin target form.
- Verification:
  `cargo test -p gated-protocol-kubernetes`,
  `cargo fmt --all`,
  `pnpm exec tsc --noEmit -p tsconfig.json`,
  and `pnpm exec eslint src/features/admin/pages/config/target-form.tsx`.
  `bun test tests/kubernetes/integration.test.ts` could not run in this
  environment because `bun` is not installed.
