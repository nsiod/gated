## Description

当前 `crates/gated-protocol-http/src/api/db_query.rs` 与 `db_terminal.rs` 暴露的 `/api/db/query/:target`、`/api/db/schemas/:target`、`/api/db/tables/:target`、`/api/db/columns/:target`、`/api/db/terminal` 等接口没有接入 `RateLimiterRegistry`。SSH/MySQL/Postgres 协议侧通过 `gated-core` 的速率限制器控制并发与 QPS，HTTP 层缺失导致恶意或失控的 SQL Console 使用可直接打穿后端数据库。

验收标准：
- 每端点在 per-user 与 per-target 两个维度上接入 `RateLimiterRegistry`，配额可通过 Parameters 配置。
- 触发限流时返回 `429 Too Many Requests`，响应头包含 `Retry-After`，并记录 `tracing::warn` 审计日志。
- 新增集成测试：并发 N 次查询触发限流。
- 既有 SSH / MySQL / Postgres 侧行为不变。

## ActiveForm

为 Gateway DB 相关端点接入速率限制

## Notes

参考 `crates/gated-core/src/rate_limiting/*` 现有实现。注意现有 `RateLimiterRegistry` 是 bytes/sec 流量速率限制（针对 SSH/MySQL/Postgres wire proxy），而 HTTP 端点需要的是 request-per-minute 维度，属于新抽象而非直接复用，设计时明确区分。

### 方案（Phase 2 proposal）

覆盖端点（6 个）：

- `GET  /api/db/schemas/:target`
- `GET  /api/db/tables/:target`
- `GET  /api/db/columns/:target`
- `POST /api/db/query/:target`
- `GET  /api/mysql/terminal/:target`（WebSocket upgrade）
- `GET  /api/postgres/terminal/:target`（WebSocket upgrade）

新增组件：

1. `crates/gated-db-migrations/src/m00002_sql_console_rate_limits.rs`：为 `parameters` 表新增 `sql_console_rate_limit_per_user`、`sql_console_rate_limit_per_target` 两个 `Option<i64>` 列（null = unlimited）。注册到 `lib.rs`。
2. `crates/gated-db-entities/src/Parameters.rs`：同步加两个字段与 `get()` fallback insert 默认值（None）。
3. `crates/gated-core/src/sql_console_rate_limit.rs`（新）：
   - 基于 `governor::DefaultKeyedRateLimiter<Uuid>` 的 per-user / per-target 两个 `Option<Arc<_>>`（None = unlimited）。
   - `refresh(&self, &DbConn)` 读取 Parameters 并重建。
   - `check(user_id, target_id) -> Result<(), SqlConsoleRateLimitError>`。
4. `Services` 新增 `sql_console_rate_limiter: Arc<SqlConsoleRateLimiter>`（内部用 `parking_lot::RwLock` 或简单 `tokio::RwLock` 管理热替换）。
5. `db_query.rs` / `db_terminal.rs` 在鉴权成功、resolve target 之后、执行查询/启动 PTY 之前调用 `check`；失败返回 `429 Too Many Requests`，`Retry-After: 60` header，body `{"error": "rate limit exceeded"}`，`tracing::warn!` 审计日志带 `username/target/endpoint`。
6. `tests/db/sql-console.test.ts` 增加限流测试用例：顺序发起 N+1 次 `POST /api/db/query/:target`，第 N+1 次收到 429 + Retry-After。

默认配额：`sql_console_rate_limit_per_user=60`、`sql_console_rate_limit_per_target=120`（每分钟）。可通过 admin API 后续改表；管理 UI 暴露留给后续任务。

限流外的影响面：

- 既有 SSH / MySQL / Postgres wire proxy（`RateLimiterRegistry`）不受影响。
- Parameters 刷新：`apply_new_rate_limits` 不调用 SQL console 限流器 refresh；限流器在 `Services::new` 与每次对 Parameters 写入时重建（admin 修改流程目前是 `handler::update_parameters`，在该处加一次 `sql_console_rate_limiter.refresh().await`）。

### 风险

- 新 migration 对已部署数据库是 additive change，风险低。
- 默认 60/min per user 对 SQL Console 正常用户足够，但需在后续压测中验证。
- Parameters 表热刷新尚未建立事件通道；本次采用"修改 Parameters 的 handler 显式 refresh"的简单做法。
